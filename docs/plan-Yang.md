# 양시찬 실험망 구현 계획

작성 기준: 2026-11-06. 목표는 첫 통합 시나리오 D2와 T2를 실제 Docker 실험망에서 각각 정상 → 장애 → 정상으로 재현하고, 심판이 기존 Lab 인터페이스로 호출하게 만드는 것이다. 이후 단일 장애를 확장한다. 아래 계획과 현재 구현 상태를 함께 관리한다.

## 첫 통합 구현과 공동 검토 결과

정상망, D2·T2의 주입·관측·복구, 실제 캡처와 심판 호출을 구현했다. 실제 클래스는 기존 Lab 계약을 유지하면서 `netrunner/docker_lab.py`에 분리했다. 라우터 주소는 Docker 기본 게이트웨이와 겹치지 않도록 각 대역의 `.254`를 사용한다.

검토 전용 에이전트의 독립 정적 검토와 실제 Docker 검사로 발견한 문제를 보완했다. 캡처 시간 초과 후 원격 프로세스 그룹 정리, 원본 pcap 번호와 총 개수, 초기 장애 복구 재시도, DNS 적용 확인, 시간 초과 전 출력 보존, 명시 포트 0 거부, tracepath 설치를 반영했다. 전체 테스트 63개가 통과했으며 실제 주입 후 실패 상황의 복구도 포함한다.

캡처의 `stdout`은 원본 출력이며, `output`은 `#<번호>`로 표시한 출력, `packets`는 원본 pcap의 패킷 수, `file`은 캡처 경로다. 이 정보의 Diagnoser Probe 연결과 실제 모델 진단은 후속 통합 범위다. 한 실험망의 실행은 순차로만 지원하며, 나머지 장애 확장은 아래 4단계에 남아 있다.

## 담당 범위와 근거

- `README.md`: 양시찬 담당은 `netrunner/lab.py`의 Lab 구현과 `config/lab.json`이다.
- `NetRunner_Breaker_vs_GLM_4인_역할분담과_개발계획.docx`: Docker 실험망, 장애 주입·해제, 클라이언트 위치의 캡처, 장애별 재현 절차, 반복 측정과 정상화 확인을 맡는다. 본인 모듈의 테스트와 보고서 단락도 작성한다.
- `docs/interfaces.md` 2절과 구현 순서: 네 Lab 함수와 LabResult 형식을 유지하며, 첫 목표는 `fixtures/first_integration`의 D2와 T2다.
- 원안은 11주차 장애 6종을 제시하지만, 후속 인터페이스 문서는 D2·T2를 먼저 하고 D1·D3·N1·S1·H1을 추가하도록 정한다. 이 계획은 현재 코드와 연결된 후속 순서를 따른다.
- 캡처 수집은 양시찬, 요약기와 진단 도구의 에이전트 연결은 이현섭, 인용 검증과 라운드 진행은 김세중, 시나리오 생성은 김승범 담당이다.

`LabInfo.load`는 domains, web_ip, subnet, enabled_faults만 읽는다. DockerLab에 필요한 hosts와 실행 경로는 별도로 같은 설정 파일에서 읽으면 된다. 기존 계약에 필드를 늘릴 필요는 없다.

## 1단계 정상 실험망

1. 루트 `compose.yaml`과 `lab/`에 이미지·서비스 설정을 만든다. 서비스는 client, router, dns, alt-dns, web을 제안한다. 원안의 네 역할 중 DNS를 두 서비스로 나누는 이유는 첫 시나리오에 기본 DNS와 독립된 정상 보조 DNS가 필요하기 때문이다.
2. client와 서버를 서로 다른 네트워크에 배치하고 router에 양쪽 인터페이스를 연결한다. 클라이언트의 서버망 경로와 서버의 반환 경로를 명시해 DNS·웹 트래픽이 router를 거치는지 확인한다.
3. 주소 초안은 서버망 `10.20.0.0/24`에 web `.10`, dns `.53`, alt-dns `.54`, router `.1`을 유지한다. 클라이언트망은 `10.21.0.0/24`로 두고 client `.2`, router `.1`을 제안한다. 기존 client `10.20.0.2`는 변경이 필요하다. 대역 충돌 확인 후 확정하고 config와 문서를 함께 갱신한다. 기존 subnet 값은 장애 대상 서버 주소의 허용 대역으로 유지한다.
4. shop.lab과 news.lab을 정상 웹 IP로 해석하게 한다. 클라이언트가 Docker 내부 DNS만 사용하거나 외부 프록시를 통해 요청하지 않도록 실제 DNS 질의와 접속 경로를 확인한다.
5. client에서 dig, curl, tcpdump를 사용할 수 있게 한다. 이후 단계에 필요한 openssl, ping, tracepath도 같은 이미지에서 제공한다. 네트워크 조작과 캡처 권한은 필요한 컨테이너에만 부여한다.

완료 조건: client에서 기본·보조 DNS가 모두 정상 IP를 반환하고, `http://shop.lab/`가 HTTP 200이다. router를 통과하는 양방향 트래픽을 캡처로 확인한다. Compose를 다시 띄워도 같은 결과가 나온다.

## 2단계 DockerLab과 첫 장애 두 개

`netrunner/lab.py`에 기존 Protocol을 만족하는 DockerLab을 추가한다. Python 표준 라이브러리 subprocess로 Compose 명령을 실행하고, 인자는 리스트로 전달한다. 명령별 시간 제한, 종료 코드, stdout·stderr를 기록한다. 실험망 밖의 대상이나 지원하지 않는 장애는 실행 전에 거부한다.

| 함수 | 구현 내용 | 성공 기준 |
|---|---|---|
| health_check(target_url) | client에서 원래 URL로 제한 시간 내 요청 | DNS와 접속이 정상이며 기대한 HTTP 200 |
| inject(fault) | 허용한 장애별 고정 명령·설정만 적용 | 명령 성공과 적용 상태 확인, 실행 내용 기록 |
| verify_symptom(scenario) | client에서 실제 DNS·접속 결과를 관측 | 아래 장애별 기대 현상과 일치 |
| reset() | DNS·웹 원본 복구, 프로젝트 전용 방화벽·tc 설정 제거, 캡처·부하 프로세스 종료 | 모든 복구 작업 성공, 반복 호출도 안전 |

- D2: 기본 DNS의 대상 도메인만 `10.20.0.99`로 바꾼다. 빈 주소 상태를 확인하고, 기본 DNS 오답·보조 DNS 정상·정상 IP로 강제 접속 시 200을 함께 확인한다. 빈 주소 접속은 환경에 따라 시간 초과 또는 도달 불가가 될 수 있으므로 예시 curl 문구와 똑같아야 한다고 가정하지 않는다.
- T2: 웹 서버의 대상 포트에 한정해 TCP RST로 거부한다. DNS는 정상이고 curl은 연결 거부로 실패하며, 캡처에서 SYN과 RST를 확인한다. 예시가 서버 발신 RST이므로 우선 웹 컨테이너의 전용 규칙으로 구현한다.
- 단순한 curl 실패만으로 재현 성공으로 처리하지 않는다. 도구 부재, DNS 기동 실패, 명령 시간 초과 등 실험망 오류와 의도한 장애를 구분한다.
- reset은 도중에 한 작업이 실패해도 나머지 복구를 시도하고 실패를 반환한다. 호스트 방화벽이나 Docker 공용 체인은 초기화하지 않는다. 정상화 최종 판정은 기존 심판의 reset 후 health_check를 이용한다.

완료 조건: 두 fixture 시나리오 각각에서 정상 → 장애별 관측 → reset → 같은 URL 200을 3회 반복하고 성공 횟수를 남긴다. 주입 중 실패한 경우에도 원복되는지 확인한다.

## 3단계 캡처와 심판 연결

1. client에서 tcpdump를 요청 전에 시작하고 준비 여부를 확인한다. 검사가 끝나면 정상 종료하고 pcap을 보존한다. 파일은 실행별로 구분해 `captures/`에 저장한다.
2. LabResult.observations에 실행 명령, 종료 코드, 원본 출력, DNS 답, HTTP 상태, 소요 시간, 캡처 경로를 넣는다. 전체 실패 시간뿐 아니라 DNS·접속 단계 측정값도 남긴다.
3. 이현섭과 client 명령 실행 방식, pcap 경로, 도구 버전, 캡처별 패킷 번호와 총 개수를 맞춘다. 장애 주입용 명령과 정답 로그는 Diagnoser에 제공하지 않는다.
4. 김세중과 실제 Lab 선택 경로를 연결한다. 기존 demo는 모의 실행임을 유지한다. 실제 실험망을 확인하는 경로는 처음에 Lab 재현·원복 검증만 수행해도 된다. ReplayDiagnoser를 연결한 경우 기록에 저장된 진단을 재생했음을 명시한다.
5. 실제 실행을 위한 지원 목록은 우선 D2·T2로 제한한다. 기존 채점 테스트는 전체 장애가 허용된 LAB 설정을 공유하므로, 지원 목록을 줄이면 N2·B1 등의 테스트가 함께 깨진다. 테스트의 전체 장애용 LabInfo를 실제 실험망 설정과 분리한다.
6. 연속 실제 실행은 reset_verified가 false면 중단한다. Referee.run_match에는 이 처리가 있지만 현재 cmd_demo의 시나리오 반복문에는 없다. 실제 실행 경로에서도 보장한다.

완료 조건: Referee가 실제 Lab을 호출하고 두 라운드의 lab_log와 reset_verified를 남긴다. 실제 출력과 실제 pcap을 열 수 있다. 저장된 diagnosis.json의 probe·패킷 번호를 실제 실행 증거로 간주하지 않는다. 실제 진단의 채점은 Diagnoser 연결 후 별도로 검증한다.

## 4단계 장애 확장과 일정

문서상 주차 일정을 기준으로 하되, 다음 단계는 앞 단계의 재현·원복이 통과한 뒤 시작한다.

| 목표 시점 | 작업 | 완료 기준 |
|---|---|---|
| 11/10, 11주차 | 정상망, DockerLab, D2·T2와 캡처, 심판 연결 우선 | 두 시나리오 각각 3회 재현·복구 기록 |
| 11주차 후속 | D1·D3·N1·S1·H1 | 장애별 관측과 정상화 확인 |
| 11/17, 12주차 | 나머지 TLS·HTTP·경로 단일 장애 확대, 실제 Diagnoser 연결 | 고정 세트 15개 재현성 확인 지원 |
| 11/24, 13주차 | 전체 16종 목표, 관측 가능한 복합 장애 확인 | 고정 세트 30개 동결에 필요한 재현 기록 |
| 12/1, 14주차 | 반복 실험, 환경·설정·측정 한계 정리 | 조건별 3회 실험과 보고서 담당 단락 |
| 12/8, 15주차 | 다른 팀원 환경에서 재실행, 시연 준비 | 실행 절차, 원본 증거, 시연 녹화 |

- S1·S2는 실험용 CA와 정상 인증서를 먼저 준비하고 client가 그 CA를 신뢰하게 한다. 정상 HTTPS부터 성공해야 하며 검증을 끄는 curl 옵션으로 우회하지 않는다.
- H1은 실제 upstream 중단으로 502를 만들고, H2는 제한된 횟수의 리다이렉트 검사로 재현한다.
- D4는 선택한 DNS 트래픽·도메인에만 영향을 주는지 확인한다. N1·N2는 지정 인터페이스와 방향, 표본 수를 기록하고 주입 값과 관측 값이 같은 의미인지 구분한다.
- N3는 작은 요청 성공·큰 전송 정지와 ICMP 상태를 함께 확인한다. N4는 제한 대역과 배경 트래픽, 무부하·부하 지연을 함께 측정하고 부하 프로세스까지 원복한다.
- B1은 ClientHello의 SNI를 관측 가능한 조건에서 실험하고 문자열 규칙의 재현 한계를 명시한다. B2는 차단 안내용 IP의 실제 응답도 준비한다.
- 복합 장애는 규칙과 tc 설정이 덮어써지지 않는지, 선행 장애에 가려지는 장애가 계약의 observable 판정과 맞는지 확인한다. 일정을 줄여야 하면 단일 장애와 첫 두 시연을 먼저 완성한다.

## 변경 파일과 검증 범위

| 경로 | 변경 범위 |
|---|---|
| compose.yaml, lab/ | 컨테이너, 라우팅, DNS·웹 원본 설정, 실행 환경 |

| config/lab.json | 확정 주소, 실제 지원 장애 목록 |
| netrunner/__main__.py | 심판 담당과 실제 실행 경로 연결 및 복구 실패 시 중단 |
| tests/test_lab.py, tests/test_judge.py | 명령 실패·시간 제한·반복 복구 검사, 전체 장애용 테스트 설정 분리 |

| fixtures/first_integration/ | 기존 시나리오를 그대로 우선 사용. 모의 진단은 예시로 유지 |

새 의존성이나 별도 오케스트레이터는 추가하지 않는다. 기존 Referee, LabResult, FaultSpec, Scenario와 표준 라이브러리를 재사용한다. Breaker·Diagnoser 모델 구현, 채점 개편, 결과 UI 개편은 이 작업 범위에 넣지 않는다.

계획 작성 시 첫 통합 시나리오 두 개는 `python3 -m netrunner validate`를 통과했다. `python3 -m pytest tests -q`는 현재 Python에 pytest가 없어 실행하지 못했다. Docker 실행 가능 여부와 실제 컨테이너 권한은 확인하지 않았으며, 1단계에서 확인한다. 소스 코드는 변경하지 않았다.
